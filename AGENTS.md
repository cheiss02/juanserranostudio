# Repository Notes

- This is a small set of self-contained static pages — no framework, no bundler, no build step.
  - `index.html` is the homepage: a Fibonacci-sphere sports photo archive (splash, intro film, drag-to-rotate sphere, flat grid, lightbox). Sphere cards take each photo’s real shape from the `ASPECT` map in `script.js` (add an entry when adding a photo), and `computeLayout()` shrinks the sphere until every card fits inside the screen with a gutter. A Back button returns from the zoomed-in sphere/grid. Its CSS is `style.css`; its behavior is `script.js` (sphere/grid/lightbox-specific, not shared). Its header now uses the same always-visible `.site-nav` as every other page (no more hamburger/full-screen overlay — that was deliberately unified for consistency).
  - Every page shares `style.css` and `nav.js` for the header nav (`.site-nav`: Portfolio/Services/About/Contact + EN/ES) and language toggle. Secondary pages (`portfolio.html`, `sport.html`, `quinceanera.html`, `wedding.html`, `photobooth.html`, `portraits.html`, `services.html`, `about.html`, `contact.html`, `privacy.html`, `terms.html`) each define their own `UI` translation object inline and call `initSiteChrome(UI)`.
  - The 5 gallery pages (`sport.html`, `wedding.html`, `quinceanera.html`, `photobooth.html`, `portraits.html`) pre-render every photo as static `<figure><img alt><figcaption></figure>` HTML (real content, crawlable without JS — important for AI crawlers that don't execute JavaScript), and call `nav.js`'s `initGallery({folder, photos})` to enhance that existing markup: wires up the in-page lightbox (title/place/description; closes via Close or Escape, never a new tab) and language swapping. `initGallery` does **not** create the figures — if you add a photo, add both the static `<figure>` and the matching entry in the `photos` array (same order), or they'll drift out of sync.
- Bilingual (EN/ES) throughout via `data-i18n` / `data-i18n-html` attributes + a `UI` dictionary per page (see `script.js`'s `applyLang()` for the homepage, `nav.js`'s `initSiteChrome()`/`initGallery()` for the rest). When adding copy, add both languages together.
- Category order, set by the client, is: Quinceañera, Wedding, Photo Booth, Photoshoots, Sport. Keep `services.html`'s service rows and `portfolio.html`'s category tiles in that same order. The fourth service is labelled "Photoshoots" on `services.html`; its portfolio category and page are still named "Portraits" (`portraits.html`) until the client says to rename them.
- Media lives in `assets/`: `assets/intro.mp4` (currently absent — gracefully falls back to the gradient), `assets/avatar.jpeg` (Juan's portrait, also used on `about.html`), `assets/logo-white.png` (original color logo, used for favicons) + `assets/logo-mono.png` (white silhouette, used in header/splash) + `assets/logo-color.png` (unprocessed backup), `assets/photos/01.jpg`–`18.jpg` (18 unique real sports photos, including 5 FIFA World Cup 2026 Final Draw portraits — the homepage sphere cycles them into 21 slots; `sport.html` shows all 18 once each), `assets/wedding/01-04.jpg`, `assets/quinceanera/01-07.jpg`, `assets/portraits/01-06.jpg`, `assets/services/photobooth.jpg` (stock example photo, credited on-page — no real photo booth photo exists yet). All real photos are the client's own; downscaled to ~2000px/85% quality on import, never committed at original multi-MB size. Every photo folder also has a `thumbs/` copy (≤760px for `photos/`, ≤900px elsewhere, JPEG q78) that pages and the homepage sphere display; the full-size file is only loaded in the lightbox. **When adding a photo, also generate its `thumbs/` copy** (and add its aspect to `ASPECT` in `script.js` if it’s in `photos/`). `assets/avatar-sm.jpg` (240px, homepage bio) and `assets/avatar-md.jpg` (640px, about page) are resized copies of `avatar.jpeg`. More real photos are expected over time — ask before assuming a category's photo count is final.

Every page has canonical/Open Graph/Twitter Card tags; `index.html` additionally carries `ProfessionalService` JSON-LD structured data. Keep all four in sync when pages are added/renamed, and remember they must be added to `deploy.yml`'s staging step too (see below) — being a root file doesn't get them published automatically.

- GitHub Pages is driven by `.github/workflows/deploy.yml`, which stages only the actual site files (`*.html`, `style.css`, `script.js`, `nav.js`, `CNAME`, `assets/`) into a clean `_site/` directory before publishing — it does **not** publish the whole repo root. If you add a new top-level file type the site needs (e.g. another shared `.js`/`.css` file), add it to that staging step too, or it won't deploy; new `.html` files are picked up automatically via glob. `.claude/`, `AGENTS.md`, `CLAUDE.md`, `README.md`, and `.github/` are intentionally excluded from the published site. Open any `.html` file in a browser, or serve the folder with a static file server, to preview locally — there is nothing to build.
- `CNAME` at the repo root configures the `juanserranostudio.com` custom domain for GitHub Pages; keep it unless the domain changes. The site is live from `main`; confirm with the user before pushing to `main` or changing DNS/Pages settings.
- Do not add server-only secrets to client code — these are static pages with no backend.
- `.claude/skills/` holds installed Claude Code skills (impeccable, transitions-dev/-polish/-ui-generation, gsap-*, make-interfaces-feel-better, motionsites-web-builder) for UI/motion polish work on this project. `.claude/settings.local.json` is personal-local and gitignored — don't commit it.
- Every page links `style.css?v=…`, `nav.js?v=…` (and `index.html` `script.js?v=…`) with a shared timestamp version. GitHub Pages serves them with `max-age=600` and iOS Safari caches longer, so **bump the `?v=` value on all pages whenever CSS/JS changes** or phones keep showing the old styles.
